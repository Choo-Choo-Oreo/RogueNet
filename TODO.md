## Multiplayer and structure

### Networking audit of the 2026-09-23 enemy AI pass (agent-run audit, not yet playtested)
- [✗] **Enemies fully diverge per peer, top severity.** `EnemySpawning.gd` builds its own `RandomNumberGenerator` and calls `rng.randomize()` (not seeded from `NetworkSync`'s shared `mission_seed`/`dungeon_seed`, unlike the dungeon layout itself — see the confirmed-correct pattern below); spawn gating also depends on each client's own local fog-of-war (`LightMap.is_tile_lit()`, which reads that peer's own `_local.reached`). Enemies are plain `instantiate()`/`add_child()` with no `MultiplayerSynchronizer`/authority wiring at all. Result: two players in the same dungeon can see different enemy types in different places, and a single peer can double-spawn on a revisited cell (the "no already-spawned memory" behavior `EnemySpawning.gd`'s own doc comment calls out as intentional is fine solo, not fine multiplayer). Fix direction: make enemies host-authoritative/spawned-once (mirror the `PlayerSpawner.gd` pattern already used for players) and seed `EnemySpawning` off the shared dungeon seed instead of `randomize()`
- [✗] **Damage/death resolved entirely client-local.** `PlayerController._try_attack()` calls `enemy.take_damage()` directly on whatever's in that client's own scene tree; no RPC anywhere in `EntityStats.gd`, `EnemyController.gd` or `PlayerController.gd`. One player can see an enemy die while a teammate is still fighting it alive; player death/ghost state is also never told to other clients. Fix direction: route hits through the host (attacker reports a hit, host applies `EntityStats.take_damage`/emits `died`, then relays health/death to all peers)
- [✗] AI targeting/pathing (`EnemyController._nearest_player()`, `EnemySenses.update()`, `Pathfinding.next_step`) also diverges per peer, but only because it's running against N independent enemy copies — a symptom of the spawning gap above, not its own root cause; should resolve once enemies are host-authoritative

## Networking audit (2026-09-21): verify first, then decide
Found by reading the code, nothing was playtested. For each item: first check it's a real problem, then decide the fix. Items 1 and 2 of the audit are covered above (reset_session done; late Guild click is the start-dive crash).
- [✓] Disconnect leaves the peer in `missions[x]["members"]`; a dead peer gets `rpc_id` calls and a creator who leaves orphans the mission. Fixed 2026-09-22 as part of the mission ready-up/countdown feature (needed it so an in-progress countdown actually stops when someone drops): `NetworkSync._ready()`'s `peer_disconnected` handler now erases the peer from every mission's `members`/`ready`, cancels any active countdown, and ends the mission entirely if the disconnecting peer was the creator. Untested against a real disconnect
- [✗] `PlayerSpawner` spawns everyone connected, not just the mission party (ghost avatars for players still in town, spawner errors on clients without `/root/Dungeon`). Verify: host and two clients, only two dive, look at the third's screen. Fix idea: spawn only for mission members (part of the "who is in this dive" pass)
- [✓] The dive needs the host in it: confirmed by Orea 2026-09-21 (a mission won't start without the host). Rule for now: the host always leads and is always in the dive (only the creator can start, and in shared-party mode the creator is the host). Still open for `is_dedicated`, where a client can create a mission, and for the party-lead-hosts vision; decide with the netcode decision
- [✓] (Tested by Orea 2026-09-21, big map loads at the same time for both, but the test PCs are too fast to stress it; spawning is now local per diver, so the ordering matters less) No "I'm loaded" handshake between scene change and spawn (and `_send_existing_missions` can hit a client that hasn't loaded GuildTown yet). Verify: test with a slow client or a big dungeon. Fix idea: client tells the server once its scene is ready, then the server spawns and sends state
- [✗] `receive_mission_members` also force-shows `PanelMission` for every member on any join or leave; Back in shared-party mode never leaves the mission. Verify: join a mission, press Back, have someone else join. Fix idea: split into a data update and a UI update
- [✓] Singleplayer now uses `OfflineMultiplayerPeer` (`MainMenu.gd`) and `SteamManager` only touches Steam when it is running (`SteamManager.online`); Host and Join print a message and stop when Steam is off (Singleplayer confirmed working by Orea 2026-09-21; the Host/Join message is console-only, no on-screen text yet). Singleplayer without Steam crashed on `initRelayNetworkAccess` before
- [✗] Join has no failure path: `connection_failed` only prints, the peer isn't nulled, the one-shot `connected_to_server` stays attached, a second Join double-connects, Back mid-connect frees the menu anyway. Verify: join a wrong or offline host ID twice. Fix idea: null the peer and disconnect the signal on failure, disable Join while connecting
- [✗] Edge case, seen 2026-09-21: host's Steam was in Offline mode, so the client's join sat at "connecting" forever with no message, and Host still printed "Hosting". Needed a Steam restart. Fix idea: check `Steam.loggedOn()` (and that Steam is running) in `SteamManager` and before Host / Join / Singleplayer, and show a message in the menu; add a join timeout (about 15 s) that nulls the peer and says "couldn't reach host". Also disable Join while connecting (the second press gave `ERR_CANT_CREATE`, error 20)
- [✓] Dead code removed 2026-09-21 after grepping every caller: `report_steam_id`, `report_move_state`, `_relay_move_state`, `receive_move_state` (called nothing; the last called a missing `apply_move_animation`). Kept: `peer_steam_ids` (only the host's ID is ever in it and nothing reads it), `is_dedicated` (a hand-flipped test flag, always false, read by `MainTown` and `GuildMission`). Still open: `is_dedicated` isn't synced between machines, and in dedicated mode `mission_id = creator_id` overwrites a second mission
- [✓] Player who clicked Guild after the mission started waited in the mission panel until they left and rejoined (Orea, 2026-09-21): missions now get `started = true` in `_start_mission`; `_join_mission` refuses a started mission with a chat notice; End Mission now calls `_end_mission` on every mission so town players' panels and mission lists are told. Confirmed fixed by Orea 2026-09-21
- [✓] `DungeonDebugView` no longer errors when `debug_dungeon_layout` is missing from a machine's `project.godot` (superseded: the layout printer was removed 2026-09-23; check what else differs between your two `project.godot` files)
- [✗] Position streamed every frame (`PlayerController.gd` 23-26), relayed to every peer including ones in town. Tested 2026-09-21 with the profiler: `NetworkSync` showed 7241 in / 3287 out (16-18 B each), and Orea reports the traffic slows a lot when nobody is moving, which the code doesn't explain (it sends every frame while the player is the authority; `project.godot` has no low-processor or FPS cap). Cause unknown (window focus throttling? the profiler's own sampling?), so low priority; still relayed to peers in town. Fix idea: one reliable "moving to tile X" per step (movement is tile-based). Also feeds the other-players'-lights work

- [✗] Root cause of several items above: `NetworkSync` reaches into the scene tree by hard-coded path and pushes UI changes. Bigger fix: `NetworkSync` holds the state and emits signals, scenes read it in `_ready` and subscribe. Revisit with the netcode decision

Verify: export a test build. Fix idea: strip a trailing `.remap` before checking or loading

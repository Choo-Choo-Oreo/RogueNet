### Ceilings and multiple floors (2.0, not now): audit of what it would take
Idea: a ceiling object is naturally about 35% transparent and always drawn above everything; with several floors, the ceiling fades to fully transparent as you climb, the floor below vanishes, and the upper floor's objects appear. Audit against the code as of 2026-09-24 (read, not tried):
- [✗] Draw order today (all `z_index`): tiles 1-10, doors 100, enemies and players 1000-1500, the darkness sprite `LightMap` 2000, glow tint 2001, debug draw 4000. A ceiling drawn "above everything" would sit above the darkness and glow unlit in unseen areas, so it belongs between actors (1500) and the darkness (2000), e.g. 1800, so it is lit and darkened like everything else. Ceiling art itself is easy: a placed object type with `layer: ceiling` and a modulate alpha
- [✗] Ceiling fade needs a rule for what is above you: fade only where the player stands under a ceiling object (per-object or per-room)? Undecided
- [✗] Everything else assumes ONE plane. A second floor would need a floor id on: the tile layers (`GridMover` and `LightMap` fetch one `FloorData` / `WallData` by name), `DoorRegistry` (cell to door), `FlowField`, `Pathfinding`, `RoomGraph` (static current graph), `LightFlood`, `EnemySpawning` (`Vector2i` spawn cells), room JSON (one `floor` and `walls` grid), the assembler (2D offsets), and networking (`report_position` and enemy state send a bare `Vector2`, no floor). Most of these are static singletons, so a second floor is either a second instance of the whole dungeon scene or an id threaded through each
- [✗] Cheapest 2.0 route, if it ever comes: keep each floor as its own generated dungeon scene/instance (its own seed, layers and registries) and treat stairs as a scene or instance swap, rather than stacking planes in one scene. That fits the per-party dungeon instancing vision. Do not add floor ids yet
- [✗] What to do NOW so 2.0 stays possible: give objects and overlays a `layer` field (floor / overlay / object / ceiling) from day one, keep draw order in one table instead of scattered `z_index` numbers, and avoid new static singletons that assume a single dungeon
